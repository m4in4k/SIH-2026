 IMPLEMENTATION NOTES
 - Start with unsupervised baselines such as Isolation Forest/LOF for anomaly scoring.
 - Use clustering to group behaviourally similar entities; retain the features that drove each score.
 - Preserve TXID and timestamp lineage so every alert can be traced back to source records.
 - Separate ingestion, feature generation, modelling and dashboard layers for repeatable offline runs.

                                                                          FEASIBILITY ANALYSIS

  TECHNICAL FEASIBILITY                                                                               ECONOMIC & SCALABILITY VIABILITY

  - Linux-compatible offline architecture.                                                            - Uses open-source software and commodity hardware.
  - Python-based data processing and ML pipeline.                                                     - Offline deployment reduces cloud dependency and exposure.
  - Graph layer represents IP-wallet-TXID relationships.                                              - Modular design supports additional ML models.
  - Synthetic dataset supports development and testing.                                               - Processing and graph storage can be optimized for larger datasets.
  - Open-source GeoIP data can enrich country/ASN features.
                                                                                                      KEY DIFFERENTIATORS
  OPERATIONAL FEASIBILITY
                                                                                                      Wallet-only analysis -> network + blockchain correlation
  - Read-only ingestion avoids live-system dependency.
  - Modular flow: ingestion -> correlation -> ML -> alerts.                                           Rule-only alerts -> anomaly score + confidence + evidence
  - Dashboard simplifies complex relationships.
  - Replayable datasets enable repeatable testing.                                                    Manual review -> ranked, explainable investigative leads

  RISKS & MITIGATIONS
  - False positives -> combine multiple independent signals and show evidence behind each alert.
  - Sparse or incomplete network metadata -> keep blockchain-only analysis usable as a fallback.
  - Entity-linking errors -> expose confidence and source provenance instead of asserting identity.
  - Model drift -> replay versioned datasets and compare model performance across releases.
